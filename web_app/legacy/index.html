1.1 — Introduction to Custom C++ Memory Arena Allocators

In user-space C++ applications, standard heap allocations via new or std::malloc delegate memory requests to the underlying Operating System heap manager (such as glibc ptmalloc, Microsoft CRT, or jemalloc). When a program requests a dynamic block of RAM, the allocator must search free-list bin trees, acquire thread synchronization mutexes, and potentially execute a kernel trap (brk or mmap syscall) to expand the process virtual address space. In low-latency systems such as High-Frequency Trading (HFT) matching engines or real-time physics loop engines, the resulting 100+ CPU cycle allocation cost and thread lock contention are unacceptable.

An Arena Allocator (also known as a region or bump allocator) bypasses the general-purpose OS heap manager entirely. It pre-allocates a contiguous, fixed block of raw memory at initialization time. Subsequent object allocations within the arena increment an offset pointer in contiguous RAM. Allocating memory degenerates into a single integer addition operation—executing in 1 single CPU clock cycle with 100% deterministic latency and optimal L1/L2 data cache locality.

As an aside...
Standard containers like std::vector reallocate and copy elements when capacity is exceeded, incurring unpredictable O(N) allocation spikes. By backing custom data structures with a dedicated Arena Allocator, memory layout remains strictly sequential, eliminating heap fragmentation and cache misses across high-frequency execution paths.

1.2 — Raw Memory Representation & Deconstructing std::byte[]

At the hardware interface, physical memory is an unformatted byte array indexed by numerical addresses. Prior to C++17, raw memory buffers were represented using unsigned char or void*. However, unsigned char exposes arithmetic operators that allow accidental value mutations, while void* hides size semantics and prevents pointer arithmetic without explicit casting.

C++17 introduced std::byte (defined in <cstddef>) as an explicit, distinct type representing raw, untyped memory. An array of std::byte reserves physical bytes in virtual memory without executing any object constructors or establishing type semantics.

raw_memory.cpp
1std::byte* backing_buffer; // Raw unconstructed memory pointer
// std::byte (C++17) represents raw memory. Contains no object semantics or characters.
2backing_buffer = new std::byte[256]; // Allocate 256 contiguous bytes
// Asks OS for 256 contiguous bytes. CRITICAL: NO constructors run! Contains uninitialized garbage bits.
3size_t offset = 0; // Byte offset index
// Tracks offset boundary for next placement new address calculation.

1.3 — Placement new: Constructing Objects in Pre-Allocated RAM

Standard expression new Node(args) performs two distinct steps: (1) invoking global operator new() to request memory from the OS, and (2) executing the Node constructor in the returned memory block. In custom memory allocators, step 1 is handled by our pre-allocated arena buffer.

C++ provides placement new (defined in <new>) to construct an object at a pre-determined raw memory address. By passing an explicit pointer to placement new (address) Node(args), the C++ compiler invokes the constructor in-place without calling global operator new().

placement_new.cpp
1void* raw_mem = reinterpret_cast<void*>(backing_buffer + offset);
// Computes target memory address by adding current byte offset to base pointer.
2Node* n1 = new (raw_mem) Node(3.14, 101); // Construct in-place
// Placement new: Constructs Node at raw_mem address without calling OS heap allocator.
3offset += sizeof(Node); // Advance bump pointer
// Advances offset boundary by sizeof(Node) bytes for next allocation.

1.4 — Explicit Destructor Calls & Arena Lifetime Management

Because memory allocated via placement new comes from a custom backing buffer, attempting to invoke standard delete ptr; is undefined behavior and triggers an immediate heap corruption crash (ASan attempting free on address which was not malloc()-ed). Standard delete attempts to return the pointer back to global heap free-lists.

To properly destroy objects constructed inside an arena, we must explicitly invoke the destructor member function: ptr->~Node();. This cleans up any member resources without releasing the underlying physical memory. The arena reclaiming phase is deferred until arena.reset() is called, which resets the offset back to 0 in O(1) time.

1.5 — Memory Alignment Arithmetic & Bitwise Mask Mechanics

Modern CPU architectures enforce hardware alignment restrictions when reading or writing multi-byte data types. An N-byte data type (such as an 8-byte double or 64-bit pointer) must reside at a memory address that is an exact integer multiple of N (addr % N == 0).

To enforce alignment without expensive integer modulo division (%) or branch instructions, systems allocators exploit bitwise arithmetic on powers of two (A = 2k):

1-Clock-Cycle Bitwise Alignment Formula:
aligned_address = (addr + align - 1) & ~(align - 1)

2.1 — Fixed-Size Free-List Allocators & Embedded Memory Unions

The main architectural limitation of Phase 1's linear bump allocator is its inability to deallocate individual objects independently—memory can only be reclaimed wholesale by calling arena.reset(). If an application repeatedly creates and destroys objects at runtime, a pure linear arena eventually runs out of capacity.

In Phase 2, we construct a Fixed-Size Free-List Allocator. The allocator partitions physical RAM into fixed-size chunks (e.g. 64 bytes each). When a block is unallocated, we store a 64-bit pointer inside the first 8 bytes of that block pointing to the next free chunk in memory. By overlaying a C++ union over unallocated memory blocks, we achieve zero per-block metadata overhead!

As an aside...
Embedded free-lists exploit the fact that unallocated memory cells are not actively holding user payload data. Reusing those exact byte locations to store allocation metadata nodes means our allocator overhead is strictly 0 bytes per block!

2.2 — C++ Union Overlay & 0-Byte Metadata Overhead

In C++, a union shares a single physical memory footprint between its members. When a chunk is unallocated, we interpret its memory as FreeNode free_node containing a FreeNode* next pointer. When allocated, the user writes data into std::byte data[ChunkSize]:

union_overlay.cpp
1struct FreeNode { FreeNode* next; }; // Embedded 8-byte pointer
// Embedded free-list node containing next pointer.
2union NodeUnion { // Zero-overhead memory union
// C++ Union overlaying metadata and raw user payload.
3 FreeNode free_node; // Active when chunk is free
// Active when chunk is unallocated in free-list.
4 alignas(std::max_align_t) std::byte data[ChunkSize]; // Active when allocated
// Active when chunk is allocated by user payload.
5};
// Union closing brace. Total size is exactly ChunkSize (0 overhead!).

3.1 — Variable-Size Block Allocators & Boundary-Tag Coalescing

While Phase 2's Fixed-Size Free-List achieves maximum speed for uniform blocks, real-world systems applications frequently request variable memory sizes (from 16 bytes up to several kilobytes). Fixed-size allocators suffer from severe internal fragmentation when servicing variable-size requests.

In Phase 3, we implement a Variable-Size Block Allocator utilizing Boundary Tags (Header and Footer metadata pairs). Every allocated or free block is wrapped between a Header and a Footer containing block size and allocation status. When a block is freed, the allocator inspects adjacent left and right boundary tags to perform instant O(1) block coalescing, merging neighboring free blocks into a single contiguous pool and eliminating external fragmentation!

Why do we need a Footer?
Without a Footer, deallocating a pointer only allows inspecting the right neighbor (since right_header = block_start + size). Reaching the left neighbor would require scanning the entire heap from the beginning in O(N) time! A Footer places the left block's size right behind our Header, enabling instant O(1) backward navigation!

// Footer boundary tag mirroring Header for O(1) backward coalescing.
13

17 }

18

20

21 [[nodiscard]] void* allocate(size_t size, size_t alignment = 8) {
// Best-Fit allocation with block splitting.
22 size_t needed = align_up(size + sizeof(Header) + sizeof(Footer), alignment);
// Calculates total bytes including tags.
23 std::byte* curr = m_buffer;
// Starts scanning from base buffer pointer.
24 while (curr < m_buffer + m_capacity) {
// Scans block headers.
25 Header* hdr = reinterpret_cast<Header*>(curr);
// Casts current address to Header*.
26 if (hdr->is_free && hdr->size >= needed) { // Block fits
// Checks if block fits request.
27 hdr->is_free = false; set_footer(hdr);
// Marks block allocated and updates footer.
28 return reinterpret_cast<void*>(curr + sizeof(Header));
// Returns pointer to payload space.
29 }
// If closing brace.
30 curr += hdr->size; // Move to next header
// Advances pointer by block size to next header.
31 }
// While loop closing brace.
32 throw std::bad_alloc();
// Throws bad_alloc if out of memory.
33 }
// allocate closing brace.
34
// Blank line.
35 void deallocate(void* ptr) noexcept { // Immediate O(1) coalescing
// O(1) Deallocation with Left and Right Coalescing.
36 if (!ptr) return;
// Nullptr safety check.
37 std::byte* block_start = reinterpret_cast<std::byte*>(ptr) - sizeof(Header);
// Reaches Header address.
38 Header* hdr = reinterpret_cast<Header*>(block_start);
// Casts to Header*.
39 hdr->is_free = true; set_footer(hdr);
// Marks block free and updates footer.
40 std::byte* right_ptr = block_start + hdr->size;
// Calculates right neighbor header address.
41 if (right_ptr < m_buffer + m_capacity) {
// Checks if right neighbor is inside buffer.
42 Header* r_hdr = reinterpret_cast<Header*>(right_ptr);
// Casts right neighbor to Header*.
43 if (r_hdr->is_free) { hdr->size += r_hdr->size; set_footer(hdr); } // Coalesce right
// Merges right free block in O(1) time!
44 }

45 }

46};
